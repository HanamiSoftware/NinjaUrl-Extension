# NinjaAuth Integration — NinjaURL Extension

> Branches verified: `dev` and `master`. The Background source has identical content on both branches; this guide documents that shared integration behavior.

## Responsibility split

- NinjaAuth owns OAuth Authorization Code + PKCE, code exchange, session lookup, and current-session logout.
- The Background Service Worker owns the SDK instance and initialization.
- The Background translates SDK results into Chrome runtime messages and owns the local UI cache.
- The Side Panel is a UI client; it does not implement OAuth or call Auth Worker session routes directly.

## Current Background integration

The Background on both branches loads the NinjaAuth class into its own JavaScript runtime, creates one instance with `new NinjaAuth()`, and initializes it once with:

- Extension client ID.
- `chrome.identity.getRedirectURL("auth")`.
- `platform: "extension"`.
- `environment: "development"`.

The same instance is used for login, session lookup, and logout.

### Login

1. Call SDK `login()`.
2. Call SDK `getSession()`.
3. Require an authenticated result and user.
4. Save the user profile in `chrome.storage.local`.
5. Notify the UI with `USER_UPDATED`.

### Restore

1. Read the cached user from `chrome.storage.local`.
2. If present, restore the UI immediately with `authenticated: true` and `session: null`; this cache-hit path does not call the server.
3. If absent, call SDK `getSession()`.
4. Cache the user only when the server returns an authenticated session.
5. Preserve and propagate operational errors rather than silently converting them into anonymous state.

A cache hit is presentation restoration only. It does not prove that the server session is still valid.

### Logout

1. Call SDK `logout()`.
2. Only after successful server confirmation, remove the cached user.
3. Notify the UI with the anonymous session.

If the SDK logout call fails, the current flow does not proceed to remove the cached user.

## Local link list cache — V6

The link list is separate from the cached user profile described above. In the V6 Background source inspected on Extension `dev` commit `1a5d30a0d8f59591e5baa6c425ecb061c1aa2f71`:

1. `getLinks()` reads the `links` array from `chrome.storage.local`.
2. After a successful `POST /v1/link/create`, the Background creates a local item containing `id`, `slug`, `short`, `long`, `isNew` and a client-generated `createdAt`.
3. The new item is inserted at the beginning of the array with `unshift`, preserving newest-first display order.
4. The Side Panel requests `GET_LINKS` from the Background and renders that local array. Opening the panel does not issue a database/API list request.
5. The current `DELETE_LINK` handler filters the local array and writes it back to storage. The server DELETE request is still commented out in the inspected source.

This is Chrome's `chrome.storage.local` API, not the web page `window.localStorage` API.

### Contract and limitations

- Preserve this cache-first rendering path for a fast Side Panel experience.
- Treat the list as a local UI projection, never as proof of link existence, ownership, authorization, current expiry or security status.
- The server's 90-day anonymous-link policy (ADR-001 in the Workers repository) must be enforced by the backend; a local cached item must not extend its life.
- The current `createdAt` is generated by the Extension client. It is useful for display/order of local creations but is not the authoritative server timestamp.
- Partition the cache by a stable principal/context before multi-account use; explicitly define how anonymous links are merged into an authenticated account. On logout/account switch, never render another principal's cached links. Avoid blindly deleting anonymous data before a confirmed transfer.
- Local-only deletion is not server deletion. Complete link management requires a server-backed delete and later reconciliation/refresh of the local cache.
- The inspected implementation does not demonstrate cross-device synchronization, server-backed list reconciliation or account-scoped cache isolation. Do not claim those capabilities until implemented and tested. Cache isolation is a beta-readiness gap, not merely a visual refinement.
